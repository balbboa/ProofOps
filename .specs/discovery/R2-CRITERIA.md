# Round 2 — Opportunity Search: Criteria & Method

> Date: 2026-09-23. Founder decision: **ProofOps (two-system reconciliation) = NO-GO. Not to be revived.**
> Direction under investigation (hypothesis, NOT validated): a narrow, self-service **"pre-flight / readiness gate"** for a recurring B2B workflow, where documents/data must be checked before money, a shipment, an approval, a filing or a delivery can proceed.

## Hard kill criteria (any one → KILL)

- K1. The exact core job is already sold cheaply as self-service.
- K2. The natural customer response is "use/switch to the existing system", not buying an extra product.
- K3. Differentiation is only AI + more detection + nicer UI + more automation.
- K4. The payer is unclear.
- K5. The pain is real but infrequent or non-economic.
- K6. The obvious acquisition channel requires sales calls.
- K7. The MVP needs many integrations before it is useful.
- K8. The platform owner can easily absorb the feature.
- K9. It is essentially a feature of a larger incumbent.
- K10. No plausible path to ~€1k MRR without a large customer count.
- K11 (carried from the brief). Security/regulatory burden is incompatible with a solo developer (e.g. HIPAA-heavy, bank-grade certification required to sell).

## Mandatory evidence requirement

Before recommending, there must be evidence of an **existing economic transaction** around the problem: people already spend money, time, employees, fees or lost revenue dealing with it, **and** there is a reason they would buy *this* product.

The uncomfortable question every survivor must answer:
> **"Who already pays for this exact job today, what do they pay, and why wouldn't they simply use the existing product?"**

## Must-prove table (survivors)

| Requirement | Must prove |
|---|---|
| Pain | Happens repeatedly |
| Payer | A specific person/company pays |
| Economic value | Labour, delays, errors or lost money |
| Existing workaround | Clearly documented |
| Existing products | No cheap self-serve equivalent |
| Switching behaviour | Customer wouldn't simply switch incumbent |
| MVP | One narrow workflow |
| Input | Documents/email/files accessible |
| Output | Concrete business action |
| Frequency | Weekly/daily preferred |
| Acquisition | Search/community/content/PLG |
| Price | Plausibly €30–150+/month |
| Integration | Minimal initially |
| Support | Low |
| AI dependence | Optional / bounded |
| Solo build | Feasible |

## Economics-first ordering

1. Can one customer plausibly save or protect **€300–5,000+/month** through this workflow?
2. Can we charge **€50–200/month**?
3. Can the same product work for 20 similar customers?
4. Only then: can we reach €1k MRR?

## Funnel

- **Stage A:** ~20+ workflow candidates across industries.
- **Stage B:** per candidate, evidence of pain, current solutions and pricing, economic behaviour, and the competitive gap.
- **Stage C:** kill aggressively (expect 15–19 of 20 to die).
- **Stage D:** deep-dive 2–3 survivors (demand, intent, competitors, pricing, onboarding, APIs, sample docs, complexity, distribution).
- **Stage E:** real-world validation only if something survives.

## Founder constraints (unchanged)

Solo side-project developer in Brazil. About €35/month budget. No sales calls. Low support burden. Sandbox/public data only during development.
